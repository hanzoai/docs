---
title: Platform Sandboxing
description: How macOS, Linux and Windows enforce the Hanzo Dev sandbox.
---

The [sandbox mode](/docs/dev/configuration/sandbox) is enforced by the operating system. `dev sandbox -- <command>` runs a command under the same enforcement.

## macOS

Commands run under Apple Seatbelt (`/usr/bin/sandbox-exec`) with a profile built from the sandbox mode.

To see what the sandbox refused while a command ran:

```bash
dev sandbox --log-denials -- npm test
```

## Linux

Commands run under bubblewrap for the filesystem, with seccomp and `no_new_privs` applied in-process. Hanzo Dev uses `bwrap` from your `PATH`; if there is none, it uses the copy it ships and warns you.

WSL1 is not supported; use WSL2.

In a container that does not allow these mechanisms, let the container be the isolation and run with `--dangerously-bypass-approvals-and-sandbox` inside it.

## Windows

Turn the Windows sandbox on in `config.toml`:

```toml
[windows]
sandbox = "elevated"
```

`elevated` is the full sandbox and needs a one-time setup, which `/setup-default-sandbox` runs. `unelevated` runs commands with a restricted token instead. Until `[windows] sandbox` is set, Hanzo Dev runs in `read-only` even where it would otherwise use `workspace-write`.

`/sandbox-add-read-dir <absolute path>` lets the sandbox read another directory.
