**After this page you have a working credential and one call that answered.**

> Here to use Hanzo rather than call its API? [Download Hanzo Desktop](https://hanzo.ai/download), or open [hanzo.app](https://hanzo.app) in your browser: no terminal needed.
*(Deploying on your own hardware or offline? Jump straight to [Self-Hosting & Air-Gapped](/docs/self-hosting).)*

Hanzo is one cloud behind one key. Every capability — inference, identity,
storage, money, agents — answers at `https://api.hanzo.ai`, and the CLI, the
SDKs and the MCP tools are all generated from the same description of it. So
there is nothing to wire up per service: get a key once and everything is
reachable.

## 1. Install

<Tabs items={['npm', 'Script', 'Homebrew', 'From source']}>
<Tab value="npm">
```bash
npm i -g hanzo
```

Any OS, Windows included. This installs the `hanzo` launcher only; each native binary is downloaded and SHA-256 verified the first time you use it: `hanzo dev` (the coding agent), `hanzo mcp` (the MCP server over stdio), `hanzo engine serve <model>` (local inference).
</Tab>
<Tab value="Script">
```bash
curl -fsSL https://hanzo.sh | sh
```

Native binaries, checksummed, into `~/.local/bin`: the CLI, the MCP server, Hanzo Dev and ZT. `https://hanzo.sh/cli` installs the CLI alone, and `hanzo upgrade` keeps them current.
</Tab>
<Tab value="Homebrew">
```bash
brew install hanzoai/tap/hanzo
```
</Tab>
<Tab value="From source">
```bash
git clone https://github.com/hanzoai/cli && cd cli && cargo install --path .
```
</Tab>
</Tabs>

```bash
hanzo version
```

## 2. Log in

```bash
hanzo auth login
```

That opens a browser against [hanzo.ai/login](https://hanzo.ai/login), Hanzo's
sign-in page, and stores the resulting credential locally. `hanzo auth show` prints
who you are; `hanzo auth list` shows every identity on this machine and
`hanzo auth use` switches between them.

For a server, mint a key instead of logging a person in: **platform.hanzo.ai →
API keys**. A secret key resolves to *you*, so it belongs on a server and never
in a browser — [Authentication](/docs/api-keys) is the whole rule.

```bash
export HANZO_API_KEY=sk-...
```

## 3. List the models

The catalogue of models the gateway currently serves. It needs no key at all,
and it is the same operation on all four surfaces. An `id` from it is what a
request names as `model`.

<Tabs items={['CLI', 'SDK', 'HTTP', 'MCP']}>
<Tab value="CLI">
```bash
hanzo models list
```
</Tab>
<Tab value="SDK">
<Tabs items={['.ts', '.py', '.go', '.rs']}>
<Tab value=".ts">
```bash
npm i hanzoai
```

```typescript
import { AiApi, Configuration } from 'hanzoai'

const ai = new AiApi(new Configuration({ accessToken: process.env.HANZO_API_KEY }))
const { data } = await ai.getModels()
```
</Tab>
<Tab value=".py">
```bash
pip install "hanzoai>=8"   # Python 3.12 or newer
```

```python
import os
from hanzoai.cloud import ApiClient, Configuration
from hanzoai.cloud.api import AiApi

client = ApiClient(Configuration(access_token=os.environ["HANZO_API_KEY"]))
models = AiApi(client).get_models()
```
</Tab>
<Tab value=".go">
```bash
go get github.com/hanzoai/go-sdk/v8
```

```go
import hanzoai "github.com/hanzoai/go-sdk/v8"

cfg := hanzoai.NewConfiguration()
cfg.AddDefaultHeader("Authorization", "Bearer "+os.Getenv("HANZO_API_KEY"))
client := hanzoai.NewAPIClient(cfg)

models, _, err := client.AiAPI.GetModels(context.Background()).Execute()
```
</Tab>
<Tab value=".rs">
```bash
cargo add hanzo-client
```

```rust
use hanzo_client::apis::{ai_api, configuration::Configuration};

let mut cfg = Configuration::new();
cfg.bearer_access_token = std::env::var("HANZO_API_KEY").ok();

let models = ai_api::get_models(&cfg).await?;
```
</Tab>
</Tabs>

Each client is generated from the same description of the API, so the class and
the method both follow from the operation rather than from a hand-written
wrapper — and each carries every `/v1` capability, not just this one. The client
is regenerated per language on its own release schedule, so a method name here
can be a release behind the one the [reference](/docs/openapi) prints; the
reference says so on the operation when it is. [Java, Kotlin, Swift and
C++](/docs/sdks) are at earlier stages — that page says exactly which are on a
registry today.
</Tab>
<Tab value="HTTP">
```bash
curl https://api.hanzo.ai/v1/models \
  -H "Authorization: Bearer $HANZO_API_KEY"
```
</Tab>
<Tab value="MCP">
```bash
curl -X POST https://api.hanzo.ai/v1/mcp \
  -H "Authorization: Bearer $HANZO_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/list"}'
```

One endpoint, one tool per capability. `tools/call` names the capability and the
operation; `describe` explains any operation's input.
</Tab>
</Tabs>

Those are one API seen from four places, and the tabs above are the whole
difference. Pick the one you will write in:

- **[CLI](/docs/cli)** — every capability as a command group, one page each.
- **[SDKs](/docs/sdks)** — TypeScript, Python, Go and Rust on a registry today;
  Java, Kotlin, Swift and C++ behind them. Generated from the same description
  the CLI and the tools are.
- **[MCP](/docs/mcp)** — one endpoint an agent connects to; [the tools](/docs/mcp-tools)
  are listed one per capability.

HTTP needs no page: it is `https://api.hanzo.ai` and the key you just exported.

## 4. Send a completion

This is the first step that draws down credit; everything above is free to run.
`zen5` is an `id` the catalogue lists.

<Tabs items={['CLI', 'HTTP']}>
<Tab value="CLI">
```bash
hanzo chat completions --data '{"model":"zen5","messages":[{"role":"user","content":"hello"}]}'
```
</Tab>
<Tab value="HTTP">
```bash
curl -X POST https://api.hanzo.ai/v1/chat/completions \
  -H "Authorization: Bearer $HANZO_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"zen5","messages":[{"role":"user","content":"hello"}]}'
```
</Tab>
</Tabs>

A `401` names what was missing and where a key comes from; a `402
insufficient_balance` means the key is fine and the org has no credit — see
[Credits & billing](/docs/credits). A `429` carries `Retry-After`, in seconds.

Then read what it drew down:

```bash
hanzo billing balance
hanzo usage summary
```

[Credits & billing](/docs/credits) explains what a credit is and what happens at
zero; [Pricing](/docs/pricing) is the rate for every model and tool.

## 5. Record a fact and read it back

The graph holds what is true of your org's entities, and who said so. Assert
one fact, then resolve what holds now.

```bash
curl -X POST https://api.hanzo.ai/v1/graph \
  -H "Authorization: Bearer $HANZO_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"assertions":[{"entity":"acme","relation":"owner","value":"ada","at":"2026-01-01T00:00:00Z","source":"quickstart"}]}'

curl -X POST https://api.hanzo.ai/v1/graph/resolve \
  -H "Authorization: Bearer $HANZO_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"entity":"acme","relation":"owner"}'
```

The assert answers `{"recorded":1,…}`; the resolve answers `"known":true` with
the assertion as `winner`. [Graph](/docs/openapi/graph) is the rest of it.

## 6. Run Hanzo locally (Canonical CLI Lifecycle)

The `hanzo` CLI separates the **local runtime** (VM, k3s, containerd, `hanzod`) from **platform & app workloads** (Hanzo Cloud, Engine, and your apps), so you can stop and rebuild workloads without restarting Kubernetes:

| Command | Layer | What it does |
|---|---|---|
| `hanzo start` | Runtime | Boot the local Hanzo runtime (VM, k3s, containerd) without starting workloads (`--cpus`, `--memory`, `--disk`) |
| `hanzo stop` | Runtime | Gracefully drain workloads, stop k3s and the VM, and reclaim CPU, memory, and ports |
| `hanzo restart` | Runtime | Restart the local runtime and restore previously running workloads |
| `hanzo up` | Platform & Apps | Start Hanzo Cloud and configured apps (implicitly runs `hanzo start` if stopped; supports `--cloud-only`, `--ai-only`) |
| `hanzo down` | Platform & Apps | Stop Cloud and app workloads while keeping k3s, image caches, and volumes warm (`--vm` also stops the runtime) |
| `hanzo ps` | Status | Show live status of the local runtime, k3s, Hanzo Cloud, `hanzod`, and cloud sandboxes |
| `hanzo dev` | Coding | Launch the open-source coding agent (`hanzoai/dev` / `hanzoai/gen`) |
| `hanzo status` / `hanzo doctor` | Diagnostics | Inspect system health and diagnose local runtime or credential issues |
| `hanzo reset` | State | Explicitly reset local environment state (`--all` clears cached runtime images and volumes) |

```bash
hanzo up            # boot local runtime (if needed) + Hanzo Cloud
hanzo ps            # inspect local runtime, k3s, Cloud & sandboxes
hanzo down          # stop Cloud workloads, keep k3s + image cache warm
hanzo stop          # shut down local runtime and reclaim resources
```

To run the open-source Cloud server ([`hanzoai/cloud`](https://github.com/hanzoai/cloud)) directly on loopback with zero Kubernetes or external services (requires Go `1.26.5`+ and `openssl`):

```bash
git clone https://github.com/hanzoai/cloud && cd cloud
make boot
```

In a second shell, verify health, the Base subsystem, and the MCP tool server:

```bash
curl -sS http://127.0.0.1:8080/healthz
curl -sS http://127.0.0.1:8080/v1/base/health
curl -sS -X POST http://127.0.0.1:8080/v1/mcp \
  -H "Content-Type: application/json" \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/list"}'
```

Stop the loopback server with `make dev-stop`.

To add local open-weight model inference ([`hanzoai/engine`](https://github.com/hanzoai/engine)), local OIDC identity ([`hanzoai/iam`](https://github.com/hanzoai/iam)), desktop/mobile clients ([Desktop](/docs/apps/desktop) · [Mobile](/docs/apps/mobile)), or build custom apps with the [`@hanzo/mod` App SDK](/docs/apps/mods), see [Self-Hosting & Air-Gapped](/docs/self-hosting). See [The Network](/docs/network) for joining `hanzod` compute nodes.

## When something does not answer

The CLI describes itself, so the fastest answer is usually local:

```bash
hanzo --help              # every capability as a command group
hanzo billing --help      # and every command inside one
```

Support is a capability like any other, which means you can reach it from the
same key you just exported — `hanzo help articles list` reads the knowledge
base, `hanzo help tickets` opens a ticket, and both are `/v1/help` if you would
rather call them over HTTP. [Errors](/docs/errors) explains what a status code
from `api.hanzo.ai` means before you open one.
