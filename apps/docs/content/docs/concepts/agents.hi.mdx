**इस पेज के बाद आप एक एजेंट परिभाषित कर सकते हैं, उसे काम करते देख सकते हैं, और चलते समय
उसे चला सकते हैं.**

## दो संज्ञाएँ

एक **एजेंट** एक परिभाषा है: एक मॉडल, एक सिस्टम प्रॉम्प्ट, और उपकरण नामों का एक समूह.
एक **सत्र** एक जीवित रन है — वह पंक्ति जिस पर हर सतह अपनी गतिविधि टांगती है,
चाहे वह सतह CLI हो, कंसोल, चैट या एक बॉट.

```bash
curl -X POST https://api.hanzo.ai/v1/agents \
  -H "Authorization: Bearer $HANZO_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"name":"triage","model":"zen-1","instructions":"Triage inbound issues.","tools":["search"]}'
```

```bash
hanzo agents list
```

नाम आपके संगठन में अद्वितीय है और
`^[A-Za-z0-9][A-Za-z0-9._-]{0,63}$` से मेल खाता है. आप जो मॉडल नाम देते हैं, वह गेटवे की
परोसी सूची से **परिभाषा के समय** जाँचा जाता है — टाइपिंग की गलती अभी अस्वीकार होती है,
पहले रन पर रात 3 बजे नहीं. लगातार चलने वाले एजेंट को पाँच-फ़ील्ड cron अनुसूची रखनी होती है,
और वह प्रति संगठन सीमा में गिना जाता है.

## एक प्रवाह एक वृक्ष है

```bash
curl -X POST https://api.hanzo.ai/v1/agents/sessions \
  -H "Authorization: Bearer $HANZO_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"agent":"triage"}'
```

`parentSessionId` ले जाने वाला सत्र उस सत्र का **उप-एजेंट** बन जाता है
और उसकी जड़ विरासत में लेता है. इसलिए दस उप-एजेंटों का पंखा दस असंबंधित रन नहीं है —
वह एक वृक्ष है, और `/v1/agents/sessions/{id}/tree` पूरा ग्राफ एक
पढ़ने में लौटाता है, हर नोड अपनी घटना गिनती लेकर.

सूची **केवल मूल सत्र** लौटाती है जब तक आप नीचे उतरने को न कहें. स्थिति इनमें से एक है:
`running`, `paused`, `done`, `error`.

## चल रहे सत्र को चलाना

चार आदेश, सब `/v1/agents/sessions/{id}` के नीचे: `message`, `pause`,
`resume`, `stop`.

<Callout>
**आदेश एक इरादा है, स्थिति बदलाव नहीं.** उस कॉल में कुछ भी सत्र की
स्थिति नहीं लिखता. `200` का अर्थ है कि आदेश टिकाऊ रूप से दर्ज और पहुँचाया गया —
एजेंट तय करता है कि उस पर कब कार्रवाई करे.
</Callout>

यही कारण है कि संचालन मशीनों के पार काम करता है. आपके लैपटॉप पर शुरू हुआ `hanzo code` सत्र
डैशबोर्ड द्वारा पोस्ट किए आदेशों को खाता है,
`/v1/agents/sessions/{id}/control` को पूछकर — कर्सर से नए आदेश, सबसे पुराना पहले,
लागू होने के बाद फिर नहीं पहुँचाए जाते.

दो अस्वीकृतियाँ जानने लायक हैं: **समाप्त** सत्र हर आदेश को
`409` से मना करता है, और दूसरे किरायेदार का id `404` है — कोई संगठन दूसरे के
एजेंट नहीं चलाता, और 404 यह पुष्टि नहीं करता कि id मौजूद है.

`stop` वह अपवाद है जो संकेत देने के बजाय सच में रद्द करता है.

## देखना

```
GET /v1/agents/sessions/stream
```

सर्वर-भेजे घटनाएँ: `session` फ्रेम और `event` फ्रेम, `?root=` से संकीर्ण.
यह संगठन-सीमित है और बंद होकर विफल होता है — बस किरायेदार पर छानती है, फैलने से पहले. 256 फ्रेम से
अधिक पीछे का ग्राहक गिरा दिया जाता है, धारा रोकने की अनुमति देने के बजाय,
और हर 25 सेकंड एक `: ping` आता है ताकि मरा कनेक्शन
दिखे.

बारी `/v1/agents/sessions/{id}/events` पर दर्ज होती है — संदेश, उपकरण कॉल,
उत्पन्न, लॉग, स्थिति, नियंत्रण — हर एक एकदिष्ट `seq` से उत्तर देता है. कुछ नहीं
खोता, इसलिए रन खत्म होने के बाद दोहराया जा सकता है.

## एजेंट कहाँ पहुँचता है

- **उपकरण** — [उपकरण](/docs/openapi/tools) प्रति किरायेदार उपकरण तल है जिसके माध्यम से
  एजेंट कॉल करता है.
- **संगणना** — एक [सैंडबॉक्स](/docs/concepts/sandboxes) पट्टा.
- **ज्ञान** — [स्मृति](/docs/concepts/memory).
- **मॉडल** — [ai](/docs/openapi/ai), अनुमान तल.
