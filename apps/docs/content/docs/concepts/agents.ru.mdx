**После этой страницы вы можете определить агента, смотреть, как он работает, и направлять его, пока
он выполняется.**

## Два существительных

**Агент** — это определение: модель, системный запрос и набор имён инструментов.
**Сеанс** — это живой запуск — строка, на которую каждая поверхность вешает свою активность,
будь то CLI, консоль, чат или бот.

```bash
curl -X POST https://api.hanzo.ai/v1/agents \
  -H "Authorization: Bearer $HANZO_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"name":"triage","model":"zen-1","instructions":"Triage inbound issues.","tools":["search"]}'
```

```bash
hanzo agents list
```

Имя уникально в вашей организации и соответствует
`^[A-Za-z0-9][A-Za-z0-9._-]{0,63}$`. Названная вами модель сверяется с
каталогом, который отдаёт шлюз, **в момент определения** — опечатка отклоняется сейчас,
а не в 3 часа ночи при первом запуске. Агент, который работает непрерывно, обязан нести
расписание cron из пяти полей и учитывается в пределе на организацию.

## Один поток — одно дерево

```bash
curl -X POST https://api.hanzo.ai/v1/agents/sessions \
  -H "Authorization: Bearer $HANZO_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"agent":"triage"}'
```

Сеанс с `parentSessionId` становится **подагентом** этого сеанса
и наследует его корень. Так веер из десяти подагентов — это не десять несвязанных запусков,
а одно дерево, и `/v1/agents/sessions/{id}/tree` возвращает весь граф за одно
чтение, у каждого узла свой счётчик событий.

Список возвращает **только корневые сеансы**, пока вы не попросите спуститься. Статус — один
из `running`, `paused`, `done`, `error`.

## Управление работающим сеансом

Четыре команды, все под `/v1/agents/sessions/{id}`: `message`, `pause`,
`resume`, `stop`.

<Callout>
**Команда — это намерение, а не смена состояния.** Ничто в этом вызове не пишет
статус сеанса. `200` значит, что команда надёжно записана и доставлена —
агент сам решает, когда по ней действовать.
</Callout>

Именно поэтому управление работает между машинами. Сеанс `hanzo code`, начатый
на вашем ноутбуке, потребляет команды, которые опубликовала панель, опрашивая
`/v1/agents/sessions/{id}/control` — команды новее курсора, сначала самые старые,
и после применения они больше не доставляются.

Два отказа, которые стоит знать: **завершённый** сеанс отвергает любую команду с
`409`, а id, принадлежащий другому арендатору, — это `404`. Ни одна организация не управляет
агентами другой, и 404 не подтверждает, что id существует.

`stop` — исключение, которое действительно отменяет, а не только сигналит.

## Наблюдение

```
GET /v1/agents/sessions/stream
```

События, отправляемые сервером: кадры `session` и кадры `event`, суженные через `?root=`.
Они ограничены организацией и отказывают в закрытую — шина фильтрует по арендатору до раздачи. Подписчик,
отставший больше чем на 256 кадров, отбрасывается, а не получает право застопорить
поток, и каждые 25 секунд приходит `: ping`, чтобы мёртвое соединение было
видно.

Ходы записываются в `/v1/agents/sessions/{id}/events` — сообщение, вызов инструмента,
порождение, журнал, статус, управление — каждый отвечает монотонным `seq`. Ничего не
теряется, поэтому запуск можно воспроизвести после завершения.

## До чего дотягивается агент

- **Инструменты** — [инструменты](/docs/openapi/tools) — это плоскость инструментов на арендатора, через которую
  вызывает агент.
- **Вычисления** — аренда [песочницы](/docs/concepts/sandboxes).
- **Знание** — [память](/docs/concepts/memory).
- **Модели** — [ai](/docs/openapi/ai), плоскость вывода.
