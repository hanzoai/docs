एक संगठन के अंदर का दायरा है. उनके पते अलग हैं, जीवनचक्र अलग हैं और मालिक अलग हैं.

## साइट प्रोजेक्ट — जहाँ एक साइट रहती है

एक हैंडल जिसके नीचे एक बिल्ड डिप्लॉय होता है और परोसा जाता है.

```bash
curl -X POST https://api.hanzo.ai/v1/projects \
  -H "Authorization: Bearer $HANZO_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"slug":"acme-marketing"}'
```

```bash
hanzo projects list
```

**slug** वह हिस्सा है जो भार उठाता है. यह ऑब्जेक्ट स्टोर के कुंजी खंड,
सार्वजनिक होस्ट `<slug>.hanzo.app`, और उस हैंडल में बदल जाता है जिसे बाद की हर कॉल संबोधित करती है.
यह `^[a-z0-9]([a-z0-9-]{0,38}[a-z0-9])?$` से मेल खाता है, आरक्षित लेबल अस्वीकार होते हैं,
और यह **प्रति संगठन** अद्वितीय है — किसी और के संगठन में वही slug आपसे संबंधित नहीं.
सार्वजनिक होस्टनाम, इसके विपरीत, विश्व स्तर पर अद्वितीय है और
पहले आने वाले को मिलता है.

एक बनाने पर एक डेटा स्थान और एक आधिकारिक git रिपॉज़िटरी भी बनती है, दोनों
यथासंभव प्रयास से. यह `draft` में `201` उत्तर देता है.

इसका जीवनचक्र **रिलीज़** है, वातावरण नहीं:

```
POST /v1/projects/{slug}/deploy
GET  /v1/projects/{slug}/releases
POST /v1/projects/{slug}/releases/{release}/activate
```

हर डिप्लॉय एक रिलीज़ है और किसी भी रिलीज़ को फिर से लाइव किया जा सकता है, इसलिए पीछे लौटना
आगे बढ़ने जैसा ही ऑपरेशन है. कस्टम होस्टनाम
`/v1/projects/{slug}/domains/{host}/verify` पर सत्यापित होते हैं.

सार्वजनिक रूप से प्रकाशित करना मुफ़्त है; `visibility: private` सशुल्क सुविधा है.

## IAM प्रोजेक्ट — एक संगठन के अंदर का दायरा

वह दायरा जिसे लोग तब चुनते हैं जब उनका काम टीम से नहीं, उत्पाद या ग्राहक से अलग होता है.
यह **केवल** `/v1/iam/projects` पर बनाया और हटाया जाता है,
और अनुरोध पर सत्यापित `X-Project-Id` के रूप में चलता है.

```
GET /v1/iam/projects
```

आप इसे कहीं और कभी नहीं बनाते. `/v1/platform/projects` एक *प्रक्षेपण* है —
प्रोजेक्ट और उसके नीचे कंटेनर तल ने जो रखा है — और यह
खुले तौर पर कहता है. अनुप्रयोग उसके नीचे रहते हैं:

```
/v1/platform/projects/{project}/apps/{app}
/v1/platform/projects/{project}/apps/{app}/env
/v1/platform/projects/{project}/apps/{app}/preview
```

एक API कुंजी को एक IAM प्रोजेक्ट तक सीमित किया जा सकता है. यही सामान्य तरीका है जिससे
स्टेजिंग कुंजी उत्पादन डेटा को न छू सके.

## उन्हें अलग पहचानना

| | साइट प्रोजेक्ट | IAM प्रोजेक्ट |
|---|---|---|
| **यह क्या है** | एक डिप्लॉय की गई साइट | एक संगठन के अंदर का दायरा |
| **यहाँ बनता है** | `/v1/projects` | `/v1/iam/projects` |
| **इससे पहचाना जाता है** | एक slug, प्रति संगठन अद्वितीय | एक id, `X-Project-Id` के रूप में ले जाया गया |
| **इससे संस्करणित** | रिलीज़ | कुछ नहीं — यह एक सीमा है |
| **क्षमता** | [प्रोजेक्ट](/docs/openapi/projects) | [iam](/docs/openapi/iam) |

अंगूठे का नियम: **अगर आप बाइट्स डिप्लॉय कर रहे हैं, तो यह साइट प्रोजेक्ट है. अगर आप
अनुमतियाँ सीमित कर रहे हैं, तो यह IAM प्रोजेक्ट है.**
