# Architecture

Cette section explique comment Hanzo Cloud est assemblé — ce qui tourne aujourd'hui, et où la plateforme se dirige. Nous gardons les deux bien séparés : les pages produit ailleurs dans cette documentation décrivent le comportement livré, tandis que la direction de plateforme ici est un travail de conception ratifié par les [propositions d'amélioration Hanzo (HIP)](https://hips.hanzo.ai). Les principes qui portent le tout sont dans [Philosophie d'ingénierie](/docs/architecture/philosophy).

## Aujourd'hui

Hanzo Cloud est **un seul binaire Go**. Une seule clé API sur `api.hanzo.ai` atteint chaque capacité — inférence d'IA, identité, secrets, stockage, commerce, et plus — parce que ces capacités sont des **sous-systèmes natifs compilés dans ce seul binaire** (`cloud`, `CGO_ENABLED=0`, statique), chacun servi sous `/v1/<capability>` et décrit par l'unique document que le binaire émet, le `openapi.yaml` de [hanzoai/cloud](https://github.com/hanzoai/cloud). L'entrée et le routage sont eux aussi des sous-systèmes natifs, donc le binaire est son propre point d'entrée au lieu de se placer derrière une passerelle ou un étage d'entrée séparé. Cette consolidation en un seul binaire est le binaire cloud unifié (HIP-0106), déjà livré pour l'essentiel — et c'est le même binaire qui fait tourner [le réseau que vous pouvez exécuter vous-même](/docs/network).

Chaque capacité appartient exactement à l'un de **neuf domaines**. [La référence](/docs/openapi) les compte et les énumère toutes :

Quelques produits tournent encore comme applications autonomes sur leurs propres domaines — par exemple [Sign](/docs/openapi) (`esign.hanzo.ai`), [Dataroom](/docs/openapi) (`dataroom.hanzo.ai`) et [Cap Table](/docs/openapi) (`captable.hanzo.ai`) — et s'authentifient via Hanzo IAM. Ce sont les applications autonomes restantes, en cours d'absorption dans le runtime unique, et non l'état final visé.

## Direction

La plateforme converge vers un seul modèle pour faire tourner ces services : une **plateforme de plugins adossée au consensus**, où chaque service est un *plugin* enregistré dans un seul runtime cloud, et un petit plan de contrôle de consensus décide où vivent les rédacteurs de chaque plugin. C'est une direction de conception — spécifiée comme proposition brouillon, pas encore un runtime livré.

<Callout type="info">
La plateforme de plugins est décrite dans **HIP-0125 (brouillon)**. Elle s'appuie sur un ensemble de propositions liées — le runtime d'extensions dans le processus (HIP-0105), le binaire cloud unifié (HIP-0106), la réplication en flux (HIP-0107) et le transport ZAP (HIP-0114). Les propositions brouillon peuvent changer ; rien sur la [page de la plateforme de plugins](/docs/architecture/plugin-platform) n'est une fonction utilisateur livrée.
</Callout>
