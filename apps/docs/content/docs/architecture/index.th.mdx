# สถาปัตยกรรม

ส่วนนี้อธิบายว่า Hanzo Cloud ประกอบกันอย่างไร — สิ่งที่รันอยู่ในวันนี้ และแพลตฟอร์มกำลังมุ่งไปทางใด เราแยกสองเรื่องนี้ออกจากกันอย่างชัดเจน หน้าผลิตภัณฑ์ที่อื่นในเอกสารชุดนี้บรรยายพฤติกรรมที่ปล่อยแล้ว ส่วนทิศทางแพลตฟอร์มที่นี่คืองานออกแบบที่ให้สัตยาบันผ่าน [ข้อเสนอปรับปรุง Hanzo (HIP)](https://hips.hanzo.ai) หลักการที่รองรับทั้งหมดอยู่ใน [ปรัชญาวิศวกรรม](/docs/architecture/philosophy)

## วันนี้

Hanzo Cloud คือ **ไบนารี Go ไฟล์เดียว** คีย์ API เดียวที่ `api.hanzo.ai` เข้าถึงทุกความสามารถ — การอนุมาน AI, อัตลักษณ์, ความลับ, ที่เก็บ, พาณิชย์ และอื่น ๆ — เพราะความสามารถเหล่านั้นเป็น **ระบบย่อยพื้นเมืองที่คอมไพล์เข้าไบนารีเดียวนี้** (`cloud`, `CGO_ENABLED=0`, แบบสแตติก) แต่ละอย่างให้บริการใต้ `/v1/<capability>` และอธิบายด้วยเอกสารเดียวที่ไบนารีปล่อยออกมา คือ `openapi.yaml` ของ [hanzoai/cloud](https://github.com/hanzoai/cloud) อินเกรสและการจัดเส้นทางก็เป็นระบบย่อยพื้นเมืองเช่นกัน ดังนั้นไบนารีจึงเป็นจุดเข้าของตัวเอง แทนที่จะนั่งหลังเกตเวย์หรือชั้นอินเกรสแยกต่างหาก การรวมเป็นไบนารีเดียวนี้คือไบนารีคลาวด์ที่เป็นหนึ่งเดียว (HIP-0106) ซึ่งปล่อยไปแล้วเป็นส่วนใหญ่ — และเป็นไบนารีเดียวกันที่ขับเคลื่อน [เครือข่ายที่คุณรันเองได้](/docs/network)

ทุกความสามารถอยู่ในหนึ่งใน **เก้าโดเมน** พอดี [เอกสารอ้างอิง](/docs/openapi) นับและแสดงรายการทั้งหมด:

ผลิตภัณฑ์บางอย่างยังรันเป็นแอปพลิเคชันเดี่ยวบนโดเมนของตัวเอง — เช่น [Sign](/docs/openapi) (`esign.hanzo.ai`), [Dataroom](/docs/openapi) (`dataroom.hanzo.ai`) และ [Cap Table](/docs/openapi) (`captable.hanzo.ai`) — และยืนยันตัวตนผ่าน Hanzo IAM นี่คือแอปเดี่ยวที่เหลืออยู่ กำลังถูกดูดเข้าสู่รันไทม์เดียว ไม่ใช่สภาพสุดท้ายที่ตั้งใจไว้

## ทิศทาง

แพลตฟอร์มกำลังบรรจบสู่โมเดลเดียวสำหรับรันบริการเหล่านี้: **แพลตฟอร์มปลั๊กอินที่มีฉันทามติหนุนหลัง** ซึ่งแต่ละบริการเป็น *ปลั๊กอิน* ที่ลงทะเบียนเข้าสู่รันไทม์คลาวด์เดียว และระนาบควบคุมฉันทามติขนาดเล็กเป็นผู้ตัดสินว่าผู้เขียนของแต่ละปลั๊กอินอยู่ที่ใด นี่คือทิศทางการออกแบบ — ระบุเป็นข้อเสนอร่าง ยังไม่ใช่รันไทม์ที่ปล่อยแล้ว
