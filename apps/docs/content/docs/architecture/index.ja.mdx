# アーキテクチャ

この節では、Hanzo Cloud がどう組み上がっているか — 今日動いているものと、基盤が向かう先 — を説明します。二つははっきり分けています。ドキュメントのほかの製品ページは出荷済みの振る舞いを書き、ここでの基盤の方向は [Hanzo 改善提案（HIP）](https://hips.hanzo.ai) を通じて批准される設計作業です。その背後の原則は [エンジニアリング哲学](/docs/architecture/philosophy) にあります。

## 今日

Hanzo Cloud は **一つの Go バイナリ**です。`api.hanzo.ai` の一つの API キーがあらゆる能力に届きます。AI 推論、アイデンティティ、秘密情報、ストレージ、商取引、その他です。それらの能力は **その一つのバイナリにコンパイルされたネイティブなサブシステム**（`cloud`、`CGO_ENABLED=0`、静的）だからです。それぞれは `/v1/<capability>` の下で提供され、バイナリが出す一つの文書、[hanzoai/cloud](https://github.com/hanzoai/cloud) の `openapi.yaml` に記述されます。入口と経路制御もネイティブなサブシステムなので、バイナリは別のゲートウェイや入口層の後ろに座るのではなく、自分自身が入口です。この単一バイナリへの統合が統一クラウドバイナリ（HIP-0106）で、すでにかなり出荷されています。そして [自分で動かせるネットワーク](/docs/network) を動かしているのも同じバイナリです。

すべての能力は、ちょうど **九つの領域**の一つに入ります。[リファレンス](/docs/openapi) が数を数え、すべてを列挙します。

いくつかの製品は、まだ自分のドメインで独立したアプリケーションとして動いています。たとえば [Sign](/docs/openapi)（`esign.hanzo.ai`）、[Dataroom](/docs/openapi)（`dataroom.hanzo.ai`）、[Cap Table](/docs/openapi)（`captable.hanzo.ai`）で、Hanzo IAM を通じて認証します。これらは残っている独立アプリで、一つのランタイムへ吸収されている途中であり、目指す最終形ではありません。

## 方向

基盤は、これらのサービスを動かす一つのモデルへ収束しています。**コンセンサスに裏打ちされたプラグイン基盤**です。各サービスは単一のクラウンドランタイムに登録される *プラグイン* で、小さなコンセンサス制御プレーンが、各プラグインの書き手の居場所を決めます。これは設計の方向です。草案の提案として書かれており、まだ出荷されたランタイムではありません。

<Callout type="info">
プラグイン基盤は **HIP-0125（草案）** に書かれています。関連する一連の提案の上に立ちます。プロセス内の拡張ランタイム（HIP-0105）、統一クラウドバイナリ（HIP-0106）、ストリーミング複製（HIP-0107）、ZAP トランスポート（HIP-0114）です。草案は変わり得ます。[プラグイン基盤のページ](/docs/architecture/plugin-platform) にあるものは、出荷済みの利用者向け機能ではありません。
</Callout>
