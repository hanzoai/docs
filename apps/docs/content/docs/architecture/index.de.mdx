# Architektur

Dieser Abschnitt erklärt, wie Hanzo Cloud zusammengesetzt ist — was heute läuft und wohin die Plattform steuert. Wir halten beides klar getrennt: Die Produktseiten an anderer Stelle in dieser Dokumentation beschreiben ausgeliefertes Verhalten, während die Plattformrichtung hier Entwurfsarbeit ist, die über die [Hanzo-Verbesserungsvorschläge (HIPs)](https://hips.hanzo.ai) ratifiziert wird. Die Prinzipien dahinter stehen in der [Ingenieurphilosophie](/docs/architecture/philosophy).

## Heute

Hanzo Cloud ist **ein einziges Go-Binary**. Ein einzelner API-Schlüssel unter `api.hanzo.ai` erreicht jede Fähigkeit — KI-Inferenz, Identität, Geheimnisse, Speicher, Handel und mehr —, weil diese Fähigkeiten **native Subsysteme sind, die in dieses eine Binary kompiliert werden** (`cloud`, `CGO_ENABLED=0`, statisch). Jedes wird unter `/v1/<capability>` ausgeliefert und von dem einen Dokument beschrieben, das das Binary ausgibt, der `openapi.yaml` von [hanzoai/cloud](https://github.com/hanzoai/cloud). Eingang und Routing sind ebenfalls native Subsysteme, das Binary ist also sein eigener Einstiegspunkt und sitzt nicht hinter einem separaten Gateway oder einer Ingress-Stufe. Diese Konsolidierung auf ein Binary ist das vereinheitlichte Cloud-Binary (HIP-0106), bereits weitgehend ausgeliefert — und es ist dasselbe Binary, das [das Netz antreibt, das Sie selbst betreiben können](/docs/network).

Jede Fähigkeit gehört genau einem von **neun Domänen** an. [Die Referenz](/docs/openapi) zählt sie und listet sie alle:

Einige Produkte laufen noch als eigenständige Anwendungen auf eigenen Domänen — zum Beispiel [Sign](/docs/openapi) (`esign.hanzo.ai`), [Dataroom](/docs/openapi) (`dataroom.hanzo.ai`) und [Cap Table](/docs/openapi) (`captable.hanzo.ai`) — und authentifizieren sich über Hanzo IAM. Das sind die verbleibenden eigenständigen Apps; sie werden in die eine Laufzeit aufgenommen und sind nicht der vorgesehene Endzustand.

## Richtung

Die Plattform läuft auf ein Modell zum Betrieb dieser Dienste zu: eine **konsensgestützte Plugin-Plattform**, in der jeder Dienst ein *Plugin* ist, das in eine einzige Cloud-Laufzeit registriert wird, und eine kleine Konsens-Steuerung entscheidet, wo die Schreiber jedes Plugins leben. Das ist eine Entwurfsrichtung — als Entwurf spezifiziert, noch keine ausgelieferte Laufzeit.

<Callout type="info">
Die Plugin-Plattform ist in **HIP-0125 (Entwurf)** beschrieben. Sie baut auf verwandten Vorschlägen auf — die prozessinterne Erweiterungslaufzeit (HIP-0105), das vereinheitlichte Cloud-Binary (HIP-0106), die Streaming-Replikation (HIP-0107) und der ZAP-Transport (HIP-0114). Entwürfe können sich ändern; nichts auf der [Seite zur Plugin-Plattform](/docs/architecture/plugin-platform) ist eine ausgelieferte Nutzerfunktion.
</Callout>
