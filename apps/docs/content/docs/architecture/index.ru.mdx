# Архитектура

Этот раздел объясняет, как собран Hanzo Cloud — что работает сегодня и куда идёт платформа. Мы держим это раздельно: страницы продуктов в остальной документации описывают уже выпущенное поведение, а направление платформы здесь — проектная работа, которую утверждают через [предложения по улучшению Hanzo (HIP)](https://hips.hanzo.ai). Принципы, на которых всё держится, — в [Инженерной философии](/docs/architecture/philosophy).

## Сегодня

Hanzo Cloud — это **один двоичный файл Go**. Один ключ API на `api.hanzo.ai` достаёт до каждой возможности — инференс ИИ, удостоверение, секреты, хранение, коммерция и другое — потому что эти возможности являются **нативными подсистемами, скомпилированными в этот один файл** (`cloud`, `CGO_ENABLED=0`, статический). Каждая обслуживается по `/v1/<capability>` и описана единственным документом, который выдаёт файл, — `openapi.yaml` репозитория [hanzoai/cloud](https://github.com/hanzoai/cloud). Вход и маршрутизация тоже нативные подсистемы, поэтому файл сам является точкой входа и не стоит за отдельным шлюзом или уровнем входа. Это сведение в один файл и есть единый облачный двоичный файл (HIP-0106), уже в основном выпущенный — и тот же файл приводит в действие [сеть, которую можно запустить самому](/docs/network).

Каждая возможность входит ровно в один из **девяти доменов**. [Справочник](/docs/openapi) считает их и перечисляет все:

Несколько продуктов всё ещё работают как отдельные приложения на своих доменах — например [Sign](/docs/openapi) (`esign.hanzo.ai`), [Dataroom](/docs/openapi) (`dataroom.hanzo.ai`) и [Cap Table](/docs/openapi) (`captable.hanzo.ai`) — и проходят аутентификацию через Hanzo IAM. Это оставшиеся самостоятельные приложения: их вбирает единая среда выполнения, и это не задуманное конечное состояние.

## Направление

Платформа сходится к одной модели запуска этих служб: **платформа плагинов на консенсусе**, где каждая служба — *плагин*, зарегистрированный в единой облачной среде, а небольшая консенсусная плоскость управления решает, где живут писатели каждого плагина. Это направление проектирования — оно задано как черновое предложение, а не как выпущенная среда.

<Callout type="info">
Платформа плагинов описана в **HIP-0125 (черновик)**. Она опирается на связанные предложения — среду расширений внутри процесса (HIP-0105), единый облачный двоичный файл (HIP-0106), потоковую репликацию (HIP-0107) и транспорт ZAP (HIP-0114). Черновики могут меняться; ничего на [странице платформы плагинов](/docs/architecture/plugin-platform) не является выпущенной пользовательской функцией.
</Callout>
