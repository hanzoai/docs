# 架构

这一节说明 Hanzo Cloud 是怎样拼在一起的 — 今天在跑什么，平台要去哪里。我们把两件事分开：文档别处的产品页描述已经交付的行为，而这里的平台方向是经由 [Hanzo 改进提案（HIP）](https://hips.hanzo.ai) 批准的设计工作。背后的原则见 [工程哲学](/docs/architecture/philosophy)。

## 今天

Hanzo Cloud 是 **一个 Go 二进制文件**。`api.hanzo.ai` 上的一把 API 密钥就能到达每一项能力 — AI 推理、身份、机密、存储、商业，以及更多 — 因为这些能力是 **编译进这一个二进制文件的原生子系统**（`cloud`、`CGO_ENABLED=0`、静态链接）。每一项都在 `/v1/<capability>` 下提供，并由二进制文件发出的那一份文档描述，也就是 [hanzoai/cloud](https://github.com/hanzoai/cloud) 的 `openapi.yaml`。入口和路由同样是原生子系统，所以这个二进制文件自己就是入口，而不是坐在单独的网关或入口层后面。收成一个二进制文件，就是统一云二进制（HIP-0106），已经大体交付 — 推动 [你可以自己运行的网络](/docs/network) 的，也是同一个二进制文件。

每一项能力恰好归入 **九个域** 中的一个。[参考](/docs/openapi) 统计并列出全部：

少数产品仍作为独立应用跑在自己的域上 — 例如 [Sign](/docs/openapi)（`esign.hanzo.ai`）、[Dataroom](/docs/openapi)（`dataroom.hanzo.ai`）和 [Cap Table](/docs/openapi)（`captable.hanzo.ai`）— 并通过 Hanzo IAM 认证。它们是尚存的独立应用，正在被吸收进同一个运行时，并不是预定的终态。

## 方向

平台正在收敛到一种运行这些服务的模型：**由共识支撑的插件平台**。每项服务是注册进单一云运行时的一个 *插件*，一小块共识控制面决定每个插件的写入者住在哪里。这是设计方向 — 写成草案提案，还不是已交付的运行时。

插件平台写在 **HIP-0125（草案）** 里。它建立在一组相关提案之上 — 进程内扩展运行时（HIP-0105）、统一云二进制（HIP-0106）、流式复制（HIP-0107）以及 ZAP 传输（HIP-0114）。草案可能改变；[插件平台页面](/docs/architecture/plugin-platform) 上的内容都不是已交付的用户功能。
