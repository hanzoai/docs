# 自己的格密码：从零写的 FHE

Microsoft 有 SEAL。Zama 有 tfhe-rs。IBM 有 HElib。一个都没用。我们用 Go，从格原语写出自己的全同态加密库，带 C FFI 绑定和 Rust 接口。

这听上去像 NIH 综合征。不是。

## 为什么自己写 FHE

全同态加密让你在密文上计算，不必先解密。服务器永远看不到明文。运算发生在密文上，解密之后的结果是对的。这是加密计算的圣杯。

现成的库用特定办法、为特定用途、带着特定的性能取舍来解这个问题。SEAL 对着 Microsoft 的云计算模型做了优化。tfhe-rs 对着布尔电路求值做了优化。HElib 瞄准的是批量算术。

没有一个是为我们要的东西设计的：区块链上的加密数据库运算。我们要的同态运算，必须塞进链上存储、gas 成本和区块链状态库那套查询形态的约束里。

## 实现

底子是多项式环上的 RLWE（环上带误差学习）。环结构给出同态运算需要的代数性质，误差项给出安全性保证。

**多项式算术**：用 NTT（数论变换）做快速多项式乘法。它相当于有限域上的 FFT。朴素地乘两个 N 次多项式是 O(N^2)。NTT 把它降到 O(N log N)。在我们的参数下（N = 4096 或 8192），这是能用和不能用的差别。

**SIMD 优化**：多项式系数落在 SIMD 通道上。一条密文可以把成千上万个明文值编进并行槽位。对密文做同态运算，就是同时作用在所有槽位上。这不是 GPU 并行，是嵌在方案代数结构里的数据并行。

**自举**：FHE 的根本难题。每次同态运算都往密文里加噪声。次数够了，噪声盖过信号，解密失败。自举通过同态地求值解密函数来刷新密文——把解密本身加密。我们的自举对准的是数据库运算所需的最小电路深度，不是通用计算。

## ZapDB：加密的数据库存放

ZapDB 是 FHE 库上面的应用层。它是一个加密的键值存储，其中：

- 值以 FHE 密文存放
- 查询在密文上执行
- 数据库服务器看不到明文的值
- 结果以密文返回，只有持钥者能解密

对区块链数据库来说，节点运营者可以存状态、查状态，却始终看不到状态的真实值。隐私不是一条政策，是数学保证。

查询模型比通用数据库窄。可以做相等判断、范围查询和算术聚合。不能做任意 SQL。这是 FHE 方案所支持运算的根本限制，不是少做的功能。

## C FFI 与 Rust 绑定

核心库是 Go。决定性能的内层循环——NTT、多项式约化、噪声采样——有 C 实现，Go 经 CGO 调用。SIMD 内建函数住在 C 代码里。

Rust 绑定用安全的 Rust 类型包住 C 接口。于是我们有给 Lux 节点集成用的 Go 库、要原始性能时用的 C 库，以及栈里其余用 Rust 写的部分所用的 Rust 绑定。

```go
// Go interface
ct := fhe.Encrypt(pk, plaintext)
result := fhe.Add(ct1, ct2)
decrypted := fhe.Decrypt(sk, result)
// decrypted == plaintext1 + plaintext2
```

## 自己写为什么要紧

用别人的 FHE 库，就是把参数选择、噪声预算管理、RNG、侧信道缓解交给对方。加密数据若是公开区块链上的金融状态，全世界每个节点运营者都看得见，攻击面就不是纸上的事。

从零写，意味着每一项参数选择都说得清。我们知道 N 为什么是 4096 而不是 2048（安全余量）。我们知道系数模数为什么排成一串素数（RNS 表示，为了高效的模运算）。我们知道噪声预算花到哪里，自举之前能串多少次运算。

这种理解不在库的文档里。它来自把域算术写出来、把自举电路调通、把噪声增长实测出来。代码就是理解。
