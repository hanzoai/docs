# วิทยาการรหัสแลตทิซของเรา: FHE ที่เขียนจากศูนย์

Microsoft มี SEAL. Zama มี tfhe-rs. IBM มี HElib. เราไม่ใช้สักตัว เราสร้างไลบรารีการเข้ารหัสโฮโมมอร์ฟิกเต็มรูปแบบของเราเองจากตัวตั้งต้นของแลตทิซใน Go พร้อมตัวผูก C FFI และส่วนต่อ Rust

ฟังดูเหมือนอาการ NIH ไม่ใช่

## ทำไมต้องเขียน FHE เอง

การเข้ารหัสโฮโมมอร์ฟิกเต็มรูปแบบให้คำนวณบนข้อมูลที่เข้ารหัสแล้วโดยไม่ต้องถอดรหัส เซิร์ฟเวอร์ไม่เห็นข้อความเปิดเลย การดำเนินการเกิดบนข้อความรหัส และผลเมื่อถอดรหัสแล้วถูกต้อง นี่คือจอกศักดิ์สิทธิ์ของการคำนวณที่เข้ารหัส

ไลบรารีที่มีอยู่แก้ปัญหานี้ในแบบเฉพาะ สำหรับการใช้เฉพาะ ด้วยการแลกประสิทธิภาพเฉพาะ SEAL ถูกปรับให้เข้ากับแบบจำลองประมวลผลคลาวด์ของ Microsoft. tfhe-rs ถูกปรับให้ประเมินวงจรบูลีน HElib เล็งเลขคณิตเป็นชุด

ไม่มีตัวใดถูกออกแบบมาสำหรับสิ่งที่เราต้องการ: การดำเนินการฐานข้อมูลที่เข้ารหัสบนบล็อกเชน เราต้องการการดำเนินการโฮโมมอร์ฟิกที่อยู่ในข้อจำกัดของที่เก็บบนเชน ต้นทุน gas และรูปแบบคิวรีเฉพาะของฐานข้อมูลสถานะบล็อกเชน

## การทำให้เป็นจริง

รากฐานคือ RLWE (การเรียนรู้บนวงแหวนพร้อมค่าผิดพลาด) บนวงแหวนพหุนาม โครงสร้างวงแหวนให้สมบัติพีชคณิตที่การดำเนินการโฮโมมอร์ฟิกต้องใช้ และพจน์ค่าผิดพลาดให้หลักประกันความปลอดภัย

**เลขคณิตพหุนาม**: NTT (การแปลงเชิงทฤษฎีจำนวน) สำหรับการคูณพหุนามที่เร็ว นี่คือสิ่งที่เทียบได้กับ FFT สำหรับฟีลด์จำกัด การคูณพหุนามดีกรี N สองตัวแบบตรง ๆ คือ O(N^2). NTT ดึงลงมาที่ O(N log N). ที่พารามิเตอร์ของเรา (N = 4096 หรือ 8192) นี่คือความต่างระหว่างใช้ได้กับใช้ไม่ได้

**การปรับ SIMD**: สัมประสิทธิ์ของพหุนามลงช่องทาง SIMD ข้อความรหัสเดียวเข้ารหัสค่าข้อความเปิดได้เป็นพันในสล็อตคู่ขนาน การดำเนินการโฮโมมอร์ฟิกบนข้อความรหัสทำงานกับทุกสล็อตพร้อมกัน นี่ไม่ใช่ความขนานของ GPU — นี่คือความขนานของข้อมูลที่ฝังในโครงสร้างพีชคณิตของโครงร่าง

**การบูตสแตรป**: ความท้าทายพื้นฐานของ FHE ทุกการดำเนินการโฮโมมอร์ฟิกเติมสัญญาณรบกวนเข้าข้อความรหัส หลังดำเนินการมากพอ สัญญาณรบกวนกลบสัญญาณ และการถอดรหัสล้ม การบูตสแตรป ทำให้ข้อความรหัสสดโดยประเมินฟังก์ชันถอดรหัสแบบโฮโมมอร์ฟิก — เข้ารหัสตัวการถอดรหัสเอง การทำให้เป็นจริงของเราเล็งความลึกวงจรต่ำสุดที่การดำเนินการฐานข้อมูลต้องใช้ ไม่ใช่การคำนวณทั่วไป

## ZapDB: ที่เก็บฐานข้อมูลที่เข้ารหัส

ZapDB คือชั้นแอปพลิเคชันบนไลบรารี FHE มันเป็นที่เก็บคีย์-ค่าที่เข้ารหัส ซึ่ง:

- ค่าถูกเก็บเป็นข้อความรหัส FHE
- คิวรีวิ่งบนข้อมูลที่เข้ารหัส
- เซิร์ฟเวอร์ฐานข้อมูลไม่เห็นค่าข้อความเปิด
- ผลกลับมาเป็นข้อความรหัสที่ผู้ถือกุญแจเท่านั้นถอดได้

สำหรับฐานข้อมูลบล็อกเชน ผู้เดินโหนดเก็บและคิวรีสถานะได้โดยไม่เห็นค่าสถานะจริงเลย ความเป็นส่วนตัวไม่ใช่นโยบาย — มันเป็นหลักประกันทางคณิตศาสตร์

แบบจำลองคิวรีจำกัดกว่าฐานข้อมูลทั่วไป ตรวจความเท่ากัน คิวรีช่วง และรวมเลขคณิตได้ ทำ SQL ตามอำเภอใจไม่ได้ นี่เป็นขีดจำกัดพื้นฐานของการดำเนินการที่โครงร่าง FHE รองรับ ไม่ใช่ความสามารถที่ขาด

## C FFI และตัวผูก Rust

ไลบรารีแกนคือ Go วงในที่สำคัญต่อประสิทธิภาพ — NTT การลดพหุนาม การสุ่มสัญญาณรบกวน — มีชุดคำสั่ง C ที่ Go เรียกผ่าน CGO โค้ด C คือที่ซึ่งอินทรินซิก SIMD อยู่

ตัวผูก Rust ห่อส่วนต่อ C ด้วยชนิด Rust ที่ปลอดภัย เราจึงได้ไลบรารี Go สำหรับผสานโหนด Lux ไลบรารี C สำหรับประสิทธิภาพดิบ และตัวผูก Rust สำหรับส่วนที่เหลือของกองเราที่เขียนด้วย Rust

```go
// Go interface
ct := fhe.Encrypt(pk, plaintext)
result := fhe.Add(ct1, ct2)
decrypted := fhe.Decrypt(sk, result)
// decrypted == plaintext1 + plaintext2
```

## ทำไมการสร้างเองจึงสำคัญ

เมื่อใช้ไลบรารี FHE ของคนอื่น คุณเชื่อการเลือกพารามิเตอร์ของเขา การจัดการงบสัญญาณรบกวน RNG ของเขา และการลดช่องทางข้าง สำหรับแอปที่ข้อมูลเข้ารหัสคือสถานะการเงินบนบล็อกเชนสาธารณะ — ผู้เดินโหนดทุกคนในโลกเห็นได้ — พื้นผิวการโจมตีไม่ใช่เรื่องทฤษฎี

สร้างจากศูนย์หมายถึงเข้าใจทุกการเลือกพารามิเตอร์ เรารู้ว่าทำไม N คือ 4096 ไม่ใช่ 2048 (ระยะเผื่อความปลอดภัย) เรารู้ว่าทำไมมอดุลัสสัมประสิทธิ์ถูกจัดเป็นโซ่ของจำนวนเฉพาะ (ตัวแทน RNS เพื่อเลขคณิตมอดุลาร์ที่เร็ว) เรารู้ว่างบสัญญาณรบกวนไปทางไหน และโซ่การดำเนินการได้กี่ครั้งก่อนการบูตสแตรป

ความเข้าใจนี้ไม่มีในเอกสารของไลบรารี มันมาจากการลงมือทำเลขคณิตฟีลด์ การไล่จุดบกพร่องของวงจรบูตสแตรป และการวัดการโตของสัญญาณรบกวนจากข้อมูลจริง โค้ดคือความเข้าใจ
