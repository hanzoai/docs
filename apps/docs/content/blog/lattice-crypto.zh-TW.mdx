# 我們自己的格密碼：從空白寫起的 FHE

Microsoft 手上有 SEAL。Zama 手上有 tfhe-rs。IBM 手上有 HElib。三套都沒碰。我們用 Go，從格的基本運算寫出自己的全同態加密程式庫，附上 C FFI 的銜接和 Rust 介面。

聽起來像 NIH 症候。其實不是。

## 為什麼要自己寫 FHE

全同態加密讓計算發生在密文上，不必先解開。伺服器始終看不到明文。運算在密文上進行，解開之後的結果是對的。這是加密計算一直想拿到的東西。

既有的程式庫用特定手法、針對特定用途、帶著特定的效能取捨來解這件事。SEAL 是對著 Microsoft 的雲端計算模型調過的。tfhe-rs 是對著布林電路求值調過的。HElib 瞄準的是成批算術。

沒有一套是為我們要的東西設計的：在區塊鏈上做加密的資料庫運算。我們要的同態運算，必須塞進鏈上儲存、gas 成本，以及區塊鏈狀態庫那種查詢形態的限制裡。

## 怎麼做

底層是多項式環上的 RLWE（環上帶誤差的學習）。環的結構給出同態運算要的代數性質，誤差項給出安全性的保證。

**多項式算術**：用 NTT（數論轉換）做快速的多項式乘法。它相當於有限體上的 FFT。笨辦法乘兩個 N 次多項式是 O(N^2)。NTT 把它降成 O(N log N)。在我們的參數下（N = 4096 或 8192），這就是能用和不能用的分野。

**SIMD 最佳化**：多項式係數落在 SIMD 通道上。一條密文可以把成千上萬個明文值編進平行槽。對密文做同態運算，就是同時作用在所有槽上。這不是 GPU 的平行，是嵌在方案代數結構裡的資料平行。

**自舉**：FHE 真正難的地方。每次同態運算都往密文加雜訊。次數夠了，雜訊蓋過訊號，解密就失敗。自舉是同態地去求值解密函式，藉此刷新密文——把解密這件事本身加密。我們的自舉對準的是資料庫運算所需的最小電路深度，不是通用計算。

## ZapDB：加密過的資料庫存放

ZapDB 是 FHE 程式庫上面的應用層。它是加密的鍵值存放，其中：

- 值以 FHE 密文存放
- 查詢在密文上執行
- 資料庫伺服器看不到明文的值
- 結果以密文送回，只有持鑰的人解得開

對區塊鏈資料庫來說，節點營運者可以存狀態、查狀態，卻始終看不到狀態的真實值。隱私不是一條政策，是數學上的保證。

查詢模型比通用資料庫窄。可以做相等判斷、範圍查詢和算術聚合。不能做任意的 SQL。這是 FHE 方案所支援運算的根本限制，不是少做的功能。

## C FFI 與 Rust 繫結

核心程式庫是 Go。決定效能的內層迴圈——NTT、多項式約化、雜訊取樣——有 C 的實作，Go 經 CGO 去叫。SIMD 的內建函式住在 C 程式裡。

Rust 繫結用安全的 Rust 型別包住 C 介面。於是我們有給 Lux 節點整合用的 Go 程式庫、要原始效能時用的 C 程式庫，以及堆疊裡其餘用 Rust 寫的部分所用的 Rust 繫結。

```go
// Go interface
ct := fhe.Encrypt(pk, plaintext)
result := fhe.Add(ct1, ct2)
decrypted := fhe.Decrypt(sk, result)
// decrypted == plaintext1 + plaintext2
```

## 自己寫為什麼要緊

用別人的 FHE 程式庫，就是把參數怎麼選、雜訊預算怎麼管、RNG、旁路緩解交給對方。加密資料若是公開區塊鏈上的金融狀態，全世界每個節點營運者都看得到，攻擊面就不是紙上談兵。

從空白寫起，意思是每一項參數選擇都講得清楚。我們知道 N 為什麼是 4096 而不是 2048（安全餘裕）。我們知道係數模數為什麼排成一串質數（RNS 表示，為了有效率的模運算）。我們知道雜訊預算花到哪裡，自舉之前能串多少次運算。

這種理解不在程式庫的文件裡。它來自把體算術寫出來、把自舉電路調通、把雜訊怎麼長大實測出來。程式就是理解。
