# Своя решёточная криптография: наш FHE с нуля

У Microsoft есть SEAL. У Zama есть tfhe-rs. У IBM есть HElib. Мы не взяли ни одну из них. Мы собрали свою библиотеку полностью гомоморфного шифрования из решёточных примитивов на Go, со связками C FFI и интерфейсом на Rust.

Это похоже на синдром NIH. Это было не оно.

## Зачем писать свой FHE

Полностью гомоморфное шифрование позволяет считать над зашифрованными данными, не расшифровывая их. Сервер никогда не видит открытый текст. Операции идут над шифртекстами, и результаты после расшифрования верны. Это святой грааль зашифрованных вычислений.

Существующие библиотеки решают задачу определёнными способами, под определённые случаи, с определёнными компромиссами по скорости. SEAL оптимизирован под модель облачных вычислений Microsoft. tfhe-rs оптимизирован под вычисление булевых схем. HElib нацелен на пакетную арифметику.

Ни одна не была сделана под то, что нужно было нам: зашифрованные операции с базой на блокчейне. Нам нужны были гомоморфные операции, которые укладываются в ограничения хранения в цепи, стоимость gas и конкретные шаблоны запросов к базе состояния блокчейна.

## Реализация

Основа — RLWE (обучение с ошибками на кольце) над кольцами многочленов. Структура кольца даёт алгебраические свойства для гомоморфных операций, а члены ошибки дают гарантию стойкости.

**Арифметика многочленов**: NTT (теоретико-числовое преобразование) для быстрого умножения многочленов. Это аналог FFT для конечных полей. Наивное умножение двух многочленов степени N — это O(N^2). NTT сводит это к O(N log N). При наших параметрах (N = 4096 или 8192) это разница между пригодным и непригодным.

**Оптимизация SIMD**: Коэффициенты многочлена ложатся на дорожки SIMD. Один шифртекст может кодировать тысячи открытых значений в параллельных слотах. Гомоморфные операции над шифртекстом действуют на все слоты сразу. Это не параллелизм GPU — это параллелизм данных, встроенный в алгебраическую структуру схемы.

**Бутстреппинг**: Главная трудность FHE. Каждая гомоморфная операция добавляет шум в шифртекст. После достаточного числа операций шум забивает сигнал, и расшифрование срывается. Бутстреппинг обновляет шифртекст, гомоморфно вычисляя функцию расшифрования — шифруя само расшифрование. Наша реализация бутстреппинга целится в минимальную глубину схемы, нужную для операций с базой, а не в вычисления общего назначения.

## ZapDB: шифрованное хранение

ZapDB — прикладной слой поверх библиотеки FHE. Это шифрованное хранилище ключ-значение, в котором:

- Значения хранятся как шифртексты FHE
- Запросы исполняются над зашифрованными данными
- Сервер базы никогда не видит открытые значения
- Результаты возвращаются шифртекстами, которые расшифрует только держатель ключа

Для блокчейн-базы это значит: операторы узлов могут хранить состояние и запрашивать его, ни разу не видя настоящих значений состояния. Приватность — не политика, а математическая гарантия.

Модель запросов уже, чем у базы общего назначения. Можно проверять равенство, делать запросы по диапазону и арифметические агрегации. Произвольный SQL нельзя. Это фундаментальное ограничение операций, которые поддерживает схема FHE, а не недостающая функция.

## C FFI и привязки Rust

Ядро библиотеки — Go. Критичные по скорости внутренние циклы — NTT, приведение многочленов, выборка шума — написаны на C, и Go вызывает их через CGO. В коде C живут SIMD-интринсики.

Привязки Rust оборачивают интерфейс C безопасными типами Rust. Так мы получаем библиотеку Go для интеграции узла Lux, библиотеку C для сырой скорости и привязки Rust для всего остального нашего стека, написанного на Rust.

```go
// Go interface
ct := fhe.Encrypt(pk, plaintext)
result := fhe.Add(ct1, ct2)
decrypted := fhe.Decrypt(sk, result)
// decrypted == plaintext1 + plaintext2
```

## Почему свой код важен

Когда берёшь чужую библиотеку FHE, доверяешь её выбору параметров, её учёту бюджета шума, её RNG, её защите от побочных каналов. В приложении, где зашифрованные данные — это финансовое состояние на публичном блокчейне, видимое каждому оператору узла в мире, поверхность атаки не теоретическая.

Строить с нуля — значит понимать каждый выбор параметра. Мы знаем, почему N равен 4096, а не 2048 (запас стойкости). Мы знаем, почему модуль коэффициентов устроен как цепочка простых (представление RNS для эффективной модульной арифметики). Мы знаем, куда уходит бюджет шума и сколько операций можно сцепить до бутстреппинга.

Этого понимания нет в документации библиотеки. Оно приходит, когда реализуешь арифметику полей, отлаживаешь схему бутстреппинга и эмпирически меряешь рост шума. Код и есть понимание.
